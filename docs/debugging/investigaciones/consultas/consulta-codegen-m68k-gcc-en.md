# Consultation (EN): improving m68k codegen of our Amiga toolchain (GCC 15.1 amiga-elf g++) — flag knobs, register pinning, alternative toolchains, peephole passes

## Context

Our C++23 engine targets a **stock Amiga A500 (OCS, 68000, PAL)** and is built with the freestanding toolchain shipped with the `bartmanabyss.amiga-debug` / `vscode-amiga-debug` extension: `m68k-amiga-elf-g++ (GCC) 15.1.0`, linked with our own linker script and support `.s` files (`-nostdlib`, no libstdc++). Verified locally: `-flto` is accepted; `-mregparm=2` is **unrecognized** (it is a Bebbo `m68k-amigaos-gcc` patch, not upstream); `-mtune=68010/68020` are accepted.

The reference we compare against is `demoscene-repo-orig/effects/flatshade-convex/` compiled with **Bebbo's `m68k-amigaos-gcc` at `-O2 -fomit-frame-pointer -mregparm=2`**, whose C source also uses `register ... asm("dN")` hints. Measured in a cycle-exact emulator: reference **2.00 fields/frame (25 fps)**; our port of the *same algorithm* runs **2.31 fields (21.6 fps)**.

**The gap is pure codegen**, not algorithm: the blitter work per frame is at parity (DMA recorder: ours 62.7k vs 61.0k accesses/field include CPU+BLT+BPL; total Blitter cycles ≈ equal), the technique is identical (same per-edge EOR line blits, same single XOR area fill, same clear), and the reference has **no hand-written asm** (its `lib/lib3d/` is all `.c`; its edge is register-hinted C plus its compiler's output). Our CPU path is simply fatter: transform+visibility ≈ 90k wall cycles vs the reference's ≈71k (their own scanline profiler), per-line draw path ≈1.15k vs ≈1.0k cycles, and **CPU bus accesses/frame +45%** (51.5k vs 35.5k). Since the frame is bus/coupling-bound, that fat lands on the critical path and costs us 0.31 fields.

## What we ALREADY do (please don't re-suggest these; they are implemented or measured)

- Flags (release): `-m68000 -O2 -fomit-frame-pointer -fno-exceptions -fno-rtti -fno-strict-aliasing -ffunction-sections -fdata-sections --gc-sections`; demo TU can add `-O3` via a per-demo `build.args` (measured: +0.3 fps on the demo, **no change** when applied to engine TUs).
- Measured and rejected: `-Os` (this GCC 15.1 backend *undoes* `always_inline` at `-Os`, 11.2 fields measured; documented), `-mtune=68020` (hangs one demo's init at `-O1`), `-O0` (compiler ICE on variable shifts; only `-O2/-O3` are used), `-flto` (accepted but not yet validated end-to-end).
- Idioms already adopted after reading our own 68000 optimization manual and auditing asm: 16-bit scalar types so GCC emits native `muls.w/divu.w`; countdown loops written for `dbra`; a hand-tuned packed-multiply trick (per 3-component row: 2 `muls.w` instead of 3); shared `sincos3` per frame; zero libcalls enforced by an asm-audit tool (`__mulsi3`/`__divsi3` banned in hot paths); `always_inline`/template/scalar-traits architecture so the hot math is monomorphized into the caller.
- Register pinning status: `register const T* p __asm__("a0")` **compiles but GCC 15.1 ignores the pin**; with 6+ live pointers the backend fails with `unable to find a register to spill in class 'ADDR_REGS'`. Our manual documents this; the current escape hatch is moving the loop to a standalone `.s` routine (we have two such precedents, `support/fire_loop.s` and `support/plasma_chunky.s`, behind flags) — but the project explicitly wants to avoid per-demo hand asm and keep everything reusable in the engine.

## Questions

1. **Making GCC actually pin registers**: in GCC 14/15 (C++), is there any *supported* mechanism to get a value allocated to a specific 68000 register for the duration of a hot loop, short of an external `.s` routine? Specifically: (a) current guaranteed semantics of local register variables + `asm` operands (documented use is only "as input/output of inline asm"); (b) patterns that *do* work in practice to tie allocation through a loop (e.g. an extended-asm "frame" that wraps the loop body and lists the pinned registers as inputs each iteration, `__asm__ goto`, empty-`asm` scheduling barriers, `__attribute__((optimize))` per function); (c) any m68k-specific GCC knob for ADDR_REGS pressure / IRA allocation (`-fira-region=all`, `-fno-ira-share-save-slots`, `-fsched-*`, `-fcaller-saves` are all *accepted* by our g++ — would any of them plausibly help a 6-pointer Bresenham/transform loop, and how would you bisect it?).
2. **Toolchain alternatives**: (a) does **Bebbo's `m68k-amigaos` toolchain** ship a **g++** usable for a `-nostdlib` freestanding C++23 (templates, no exceptions/RTTI, custom linker script, our own `support/*.s`)? (b) does its GCC carry m68k **codegen** patches beyond `-mregparm` (peepholes, better address-register allocation, `dbra` generation) that would materially beat `m68k-amiga-elf-g++ 15.1` on the *same* C++? (c) is `-mregparm=2` a portable ABI patch we could apply to an amiga-elf gcc build, or does it interact badly with `-nostdlib`/asm support routines/interrupt handlers? (d) what's actually cooking for m68k in upstream GCC 15.2/16 (any relevant commits to the m68k backend)?
3. **Peephole optimizers for 68000 output**: you (Grok) reportedly know of a scene where someone bolted a **peephole optimizer onto the 68000 code** generated for the **Sega Mega Drive** (SGDK / Marsdev / m68k-elf toolchains). Which project is that exactly, is it maintained, can it consume GNU `as` output for m68k, and is it applicable to our gas `.s`/`.o` stream as a post-pass without breaking debug info (we need `-g` for our GDB/emulator flow)? Any simpler alternative (e.g., `vasm` peephole phases, `m68k-peephole`, `peep`-style tools) you would recommend testing first?
4. **If you had to bet ONE lever** to remove ~40k cycles/frame of "CPU-fat" versus this reference **without writing per-demo assembly** (i.e., via flags, compiler version/toolchain swap, backend knobs, or a post-compiler peephole pass), which one would it be, what result would you predict, and what is the cheapest falsification test? Our infra: `-S`/`objdump` audits, an asm-audit/frozen-codegen report tool, per-section cycle counters in the emulator, cycle-exact `measure-fps`, pixel freeze-diff, and an 8-frame sequence visual gate — all runnable in minutes.

Please answer with concrete, testable steps (flag names, tool URLs/repos, patch names, or code patterns), not generalities.
